# ADR 0004 — Agent-authored explanations and multi-step scenes

- **Status:** Accepted
- **Date:** 2026-10-05
- **Phase:** 6 (quality) — see [`plan/phase-6.md`](../../plan/phase-6.md)
- **Scope:** Records why explanations are authored by the host coding agent rather than
  generated by the script, and how scenes walk through code a few lines at a time.
- **Supersedes:** the deterministic narration in `src/planning/buildPlan.ts` (Phase 2) and the
  argument-free `npm run explain` flow (Phase 5).

## Context

Through Phase 5 the planner produced narration text mechanically from the diff:

> "This change updates 2 files under src/analysis. src/analysis/plan.ts is modified, with 5
> line(s) added and 2 removed. It introduces or updates buildPlan."

That text states facts about the _diff_, not what the code _does_: it lists file names and
counts, and the video shows one static block of code per scene for the whole clip. For a
viewer who does not know the language, it explains nothing. Explaining code requires reasoning
about what the code does — something a deterministic formatter cannot do.

The plugin/skill runs inside a coding agent (Codex/Claude) that already has the repository, the
diff, and the ability to read surrounding code. The overview (§5) anticipated this
("Uses the coding agent for reasoning where available"), but Phase 2 implemented a purely
deterministic planner instead.

## Decision

**1. The host coding agent authors the plan and narration; the script only renders.**

- `buildPlan` becomes `buildPlanScaffold` (`src/planning/buildPlan.ts`): it emits deterministic
  grouping, source locations, and suggested walkthrough `steps`, with **all narration blank**.
  It never invents explanations.
- `npm run plan` writes `artifacts/plan.scaffold.json`; the human/agent-readable scaffold is the
  starting point, not a finished plan.
- The orchestrator requires `--plan <path>`:
  `npm run explain -- --plan <plan.json>`. With no authored plan it exits `3` with a clear
  message. It **never** falls back to mechanical narration.
- Credentials are still pre-flighted before the plan is read, so a missing `OPENAI_API_KEY`
  fails fast with exit `4` (unchanged behaviour).
- The planned layout records both the authored plan (`authored-plan.json`) and the narrated
  plan (`plan.json`).

**2. Scenes are multi-step: they advance through the code a few lines at a time.**

- `PLAN_SCHEMA_VERSION` is **3**. `ExplainerScene` gains an optional ordered `steps:
SceneStep[]`, where each `SceneStep` is `{ narration, file, startLine, endLine }` and its
  range must sit inside one of the scene's `sourceLocations`.
- The renderer (`src/render/steps.ts`, `CodeWalkthroughScene.tsx`, `CodeFrame.tsx`) highlights
  the active step's range and scrolls to it; the highlight/scroll transition replays at each
  step boundary.
- One audio clip per scene is kept (Phase 4 invariant). `chunkTiming.ts` divides the scene's
  narration across its steps in proportion to each step's narration length; captions use the
  same windows, so caption and highlight always agree.

**3. Scaffold vs. authored plan are validated differently.**

- `validatePlan` gains `requireNarration` (default `true`). The scaffold is validated with
  `requireNarration: false`; a plan handed to the renderer requires non-empty scene narration
  and non-empty step narration.
- Step ranges are validated against the scene's source locations and the captured snapshot.

## Consequences

- For small/medium branches the agent can now write genuinely explanatory narration (what the
  code does, why it matters), assuming the viewer may not know the language.
- The "one command, no arguments" UX from Phase 5 is replaced by a scaffold → author → render
  flow; the skill (or the user) drives it. The orchestrator no longer produces narration.
- The planner is smaller and grounded only in structure; `collectSymbols` and the
  declaration-pattern narration were removed.
- Tests must supply an authored plan to the orchestrator; the offline seams
  (`EXPLAIN_BRANCH_TEST_*`) are unchanged.
- Redaction now covers step narrations (captions), not just `narrationText`.

## Alternatives considered

- **Call a chat model from the script** to write the explanations. Rejected: it adds a second
  model/provider and cost surface for something the host agent already does with better
  repository context.
- **Many small single-focus scenes** instead of multi-step scenes. Rejected: it multiplies TTS
  clips and fragments the walkthrough; per-scene clips with step windows keep sync exact and
  re-renders cheap.
- **Keeping mechanical narration as a fallback.** Rejected: a video that looks narrated but
  explains nothing is worse than a clear failure (exit `3`).
